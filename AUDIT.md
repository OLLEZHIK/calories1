# Аудит проекта fat_caunter — 2026-09-11

## Что это за проект
Многоагентная система учёта КБЖУ на Python: Telegram-бот (`bot/telegram_bot.py` — локальный polling, `api/telegram_webhook.py` — вебхук на Vercel), 8 агентов в `agents/` (Ingestion → Nutrition → Auditor → Economy/Coach/Dashboard → TeamLead-роутер → Audio), БД `database/db.py` (SQLite локально + зеркалирование в Supabase), веб-дашборд `dashboard/index.html`, деплой через `vercel.json`.

## Критический баг — вебхук падал на импорте (ИСПРАВЛЕНО)
`api/telegram_webhook.py` использовал аннотацию `Optional[Dict[str, Any]]` без `from typing import Optional, Dict, Any`. В Python аннотации типов вычисляются в момент выполнения `def`, то есть **при самом импорте модуля** — значит на каждый вызов вебхука на Vercel будет `NameError` ещё до обработки запроса. Это почти наверняка и есть причина «всё сломано»: бот через вебхук физически не мог ответить ни на одно сообщение.

Воспроизвёл ошибку изолированно, добавил импорт, повторно проверил — модуль теперь импортируется и работает.

## Баг в database/db.py — дублирующиеся функции (ИСПРАВЛЕНО)
Один из scratch-патчей (`scratch_db_patch.py`) добавил вторую пару функций `save_custom_product` / `get_custom_product`, не убрав старую. Поскольку в Python более позднее определение перекрывает раннее, реально работала урезанная версия: только точное совпадение по названию продукта и **без обращения к Supabase**.

Последствия:
- Продукты, добавленные через фото («➕ Добавить продукт»), на Vercel (где локальная SQLite лежит в `/tmp` и не переживает холодный старт) фактически переставали находиться при следующем запросе.
- Опечатки/варианты названия («творог» vs «творог 5%») не матчились.

Оставил одну консолидированную версию: локальный поиск через `LIKE` + fallback на Supabase (`ilike`). Проверил: частичные совпадения находятся, несуществующие — корректно возвращают `None`.

## Баг — вес и «активные калории» пропадали в проде (ИСПРАВЛЕНО)
`get_today_summary()` в ветке Supabase (а `USE_SUPABASE=true` — это ваш текущий режим по умолчанию) всегда возвращала жёстко заданные `DEFAULT_GOALS` и не считала `active_calories`. То есть вес (`weight_current`/`weight_goal`, которые вы выставляли через `scratch_db_fix.py`) и сожжённые калории на дашборде **никогда не подтягивались**, пока используется Supabase — только локальный SQLite-путь их учитывал.

Исправил: Supabase-ветка теперь считает `active_calories` из записей с `notes = 'Активность'` и подтягивает реальные цели (включая вес) из таблицы `user_goals` в Supabase.

**Нужно сделать руками**: в самой таблице `user_goals` на Supabase, скорее всего, нет колонок `weight_current`/`weight_goal` (в `supabase_schema.sql` их не было). Зайдите в Supabase → SQL Editor и выполните:
```sql
ALTER TABLE public.user_goals ADD COLUMN IF NOT EXISTS weight_current NUMERIC;
ALTER TABLE public.user_goals ADD COLUMN IF NOT EXISTS weight_goal NUMERIC;
```
(файл `database/supabase_schema.sql` уже обновлён с учётом этого на будущее).

## Внешняя проблема — GEMINI_API_KEY в «сломанном» формате (нужно менять руками, я это исправить не могу)
Ваш `GEMINI_API_KEY` в `.env` начинается с `AQ.` — это НЕ стандартный формат ключа Google AI Studio (обычно `AIzaSy...`). На форуме разработчиков Google (ai.google.dev) масса свежих обсуждений именно этой проблемы: ключи с префиксом `AQ.` возвращают `401 ACCESS_TOKEN_TYPE_UNSUPPORTED` и не работают ни с официальным Python SDK, ни с REST API — это известное ограничение на стороне части аккаунтов Google, а не баг в вашем коде.

Это объясняет, почему все функции на Gemini (разбор еды голосом/текстом, классификация намерений, советы тренера, распознавание фото продукта) не работали даже при исправленном коде — ключ просто не аутентифицируется.

Что делать: создать новый ключ в [Google AI Studio](https://aistudio.google.com/apikey) и проверить его формат, либо написать в саппорт/форум Google с просьбой вернуть выдачу ключей в формате `AIzaSy...` для вашего аккаунта, либо (более сложный путь) переключиться на аутентификацию через Vertex AI / service account вместо API-ключа.

Пока ключ не рабочий, система не «падает» — большинство агентов корректно уходят в fallback (Groq для распознавания еды/голоса, ключевые слова для классификации намерений), кроме одной функции: добавление продукта по фото завязано **только** на Gemini и без него не работает.

## requirements.txt — отсутствовал (ДОБАВЛЕН)
В корне проекта не было `requirements.txt`, хотя `vercel.json` собирает `api/*.py` через `@vercel/python`. Без него пакет `google-genai` не ставится на Vercel — то есть даже с рабочим ключом Gemini-функции на проде оставались бы недоступны (тихо перехватываемый `ImportError`). Добавил `requirements.txt` с `google-genai` и `python-telegram-bot`.
